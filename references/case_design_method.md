# 测试用例设计方法论：从需求点到穷举用例

这份文档讲**怎么把一句需求拆成一组测试用例**。这是本 skill 价值的核心——
需求文档里一句"识别距离 1~2m"，在合格的测试用例表里会变成 5~7 条覆盖不同
距离、角度、污损程度的用例。下面是从成熟测试用例表逆向总结的拆解套路。

## 核心心法：每个需求点都问七个问题

拿到一条需求（哪怕只是一个短语），依次问：

1. **正常路径**——最典型、参数居中的情况，必有一条。
2. **边界值**——需求里只要出现数字/阈值/范围，就在边界两侧各取点。
   - "距离 1~2m" → 0.5 / 1.0 / 1.5 / 2.0 / 2.5m（含刚超出的边界）
   - "超时 3 分钟" → 2分59秒仍亮 / 3分01秒已灭（卡着边界各一条）
   - "电量≥10% 可离开" → 9% / 10% / 50% / 100%（边界下、边界、中间、上限）
3. **分档枚举**——需求提到"不同/多种/各国"，把每一档列成独立用例。
   - "满足各国安规" → 中国220V / 美国110V / 欧洲230V / 日本100V…每国一条
   - "不同地面" → 瓷砖 / 木地板 / 短毛地毯 / 长毛地毯…每种一条
4. **异常/失败路径**——需求里的"若…则报错""失败重试""感知不到"都要单独成例。
   - "感知不到充电桩则报错" → 未放置桩 / 完全遮挡 / 报错码准确性，各一条
   - "对接失败允许重试1次" → 重试1次成功 / 重试前退出桩 / 重试后仍失败报错
5. **环境/场景变量**——光照、温度、多机多桩、行人干扰等横切维度。
   - "暗光场景对接" → <10lux触发 / 50lux摸底 / 100lux摸底 / 正常光不触发
   - "多个充电桩" → 桩间距1m / 1.5m / 2m 只点亮目标桩 / 相邻桩不误点亮
6. **干扰/鲁棒性**——防误触发、抗遮挡、并发、高频调用。
   - "只有机器人能触发亮灯" → 行人路过 / 宠物 / 车辆，逐一验证不误触发
7. **质量指标量化**——成功率、平均耗时、精度，每个指标拆成独立的性能用例。
   - "成功率100%、平均≤30s" → 成功率用例 + 平均时间用例，分开两条

并非每个需求点七问都适用——有的只产 1~2 条，有的能产十几条。判断依据是
**需求里藏了几个可变维度**，把维度逐个钉死成用例。

## 用例粒度：一条用例只验一个点

模板里用例名称几乎都是 `主题-具体场景` 的二段式，例如：
- `状态指示灯-上电接通电源`、`状态指示灯-开始充电切换`、`状态指示灯-充满切换为绿色`
- `供电兼容性-中国标准（220V/50Hz）`、`供电兼容性-美国标准（110V/60Hz）`

同一主题下的变体各自独立成行，**不要把"测试各国电压"塞进一条用例的步骤里**。
粒度细才能在测试结果列逐条标 PASS/FAIL，定位问题到具体场景。

## 字段怎么填

| 字段 | 填写要点 |
|------|---------|
| **功能模块** | 使用 `当前Sheet-子主题`，如 `重力补偿-末端识别`、`碰撞保护-阈值配置`。每组通常 2–8 条，禁止整张 Sheet 全部使用同一个模块值 |
| **用例名称** | `主题-具体场景`，二段式，必填、唯一；禁止出现 `REQ-001-正常路径` 这类机器化名称，需求编号只放 `requirement_ids` |
| **前置条件** | 只写本场景真正需要的状态，如"机器人空闲，双臂零位，末端未安装负载"；不要每条重复版本待填写、采集工具已开启等通用套话 |
| **用例步骤** | 编号步骤，多步用 `\n` 换行：`1.开启重力补偿\n2.手动拖动末端至水平位姿\n3.松手观察`。**写具体操作**，不写“设置/操作、观测/采集、记录”模板标签 |
| **预期结果** | 可判定的观测结果，带量化阈值：`位移量≤0.1cm`，而非"位移很小" |
| **用例类型** | 功能测试/性能测试/安全性测试/接口测试/可靠性测试/异常测试/耐久测试/其他测试。量化指标(成功率、耗时、精度)归性能测试；电气/安规归安全性测试；寿命/磨损归耐久测试 |
| **用例等级** | 高/中/低。主干功能与硬性指标=高；常见变体=中；极端边界/摸底=低 |

## 分类（sheet）怎么分

默认沿用需求文档的**一级业务功能模块**切分，不按“安全测试/性能测试/控制性能”
等测试视角重新归类。测试视角放在每条用例的 `type` 字段中，不能替代业务模块。

例如柔顺控制需求应优先使用：
- 重力补偿
- 拖动示教
- 碰撞保护
- 柔顺控制
- API接口
- 集成与稳定性

只有需求本身没有清晰业务章节，或用户明确要求按测试视角组织时，才使用硬件性能、
软件功能、接口测试、系统与可靠性等分类。

**按运动形态/产品形态**（适合整机/多形态产品，团队真实文件采用此法）：
- 整机功能测试 / 双臂运动形态 / 移动底盘运动形态 / 轮足运动形态 / 双足运动形态…
- 每个形态 sheet 内再按功能模块（外观尺寸/校零/移动/转向/摔倒爬起…）组织

选哪种看需求的“自然骨架”——有业务模块时按业务模块，多形态整机按产品形态分。
详见 `template_spec.md`。只有用户明确要求时才加**「概述」sheet**。

## 写出"像真人测的"用例

参考团队真实文件，好用例的预期结果往往**可观测、可记录**，而不只是"正常"：
- **量化阈值**：`位移量≤0.1cm`、`刹车距离<2m`、`偏移误差<0.5m`
- **日志/数据特征**：`日志打印 name: imu, code: 0 正常工作状态`
- **实测记录型**：有些指标先摸底，预期写`测量记录实际数据即可`（如整机净重、臂展），
  测试时把实测值填进备注——这类用 `外观检查` 或 `性能测试` 类型
- **状态/灯语**：`灯显白灯闪烁→蓝灯常亮`、`驱动器掉电黄灯`

步骤和预期都用 `1.xx\n2.xx` 编号分行，与真实文件一致。

### 禁止机器化套话

- 不把需求原句整段复制到模块名、步骤或预期结果。
- 不用“功能按需求生效”“状态变化可追溯”“不得出现未定义异常”作为通用预期。
- 不为了凑数量把每条需求机械复制成“正常路径/最小输入/越界输入/恢复稳定性”四条；
  只有存在对应业务条件时才拆分，并把场景写成真实名称。
- 日志、采样、记录动作只在该用例确实需要测量或定位问题时写入，不要求每条用例都重复。

## 用例类型怎么选

| 类型 | 适用 |
|------|------|
| 功能测试 | 功能是否正确、流程是否走通（最常用） |
| 性能测试 | 量化指标：速度/精度/时间/负载/续航 |
| 安全性测试 | 电气安全、急停、碰撞保护、认证安规 |
| 可靠性测试 | 成功率统计、长时运行、大循环耐久 |
| 稳定性测试 | 长时间运行不崩、抗干扰不失稳 |
| 异常测试 | 断电、定位丢失、堵转等异常注入 |
| 耐久测试 | 磨损、插拔寿命、腐蚀 |
| 外观检查 | 外观/尺寸/重量/丝印等目测或测量记录项 |
| 接口测试 | API/SDK 调用 |

## 用例等级的判断

- **高**：主线必过的功能、硬性合格指标（成功率、关键时间/精度、安全保护）、
  高频使用路径。这些挂了产品就不可用。
- **中**：常见但非核心的变体（中等参数、次要环境）、有容错的边界。
- **低**：极端边界摸底（超距、大角度）、能力探索性质、失败可接受或仅需记录数据。

> 部分团队在「概述」用 P0/P1/P2 风险等级替代高/中/低，脚本两者都认。

## 覆盖度自检

生成 JSON 后，对照需求逐节问自己：
- 需求里每个**数字阈值**都有边界用例了吗？
- 每个**"若…失败/异常…"**分支都有对应用例了吗？
- 每个**"支持多种/各国/不同"**都枚举展开了吗？
- 每个**量化指标**（成功率/时间/精度）都有独立性能用例了吗？
- 多形态产品：每个**形态**的每项能力都覆盖了吗？

用 `validate_cases.py` 看用例类型与等级分布——若清一色"功能测试/高"，
往往说明边界、性能、异常维度没拆够，回去补。
