## 使用约束（给分析模型）

1. 只有当 snowball 节点判定出 EtherCAT 主站(ECM)异常时才启用本依据；触发后**只分析 ethercat 节点打印内容**，不要把无关节点日志混入根因。
2. 主站异常必须给出**唯一根因结论**，并逐条对照下方规则给出：受影响电机/从站、触发原因、后续状态、排查建议。掉线电机的 slave 号一律查「二、双臂网络拓扑与从站号对照表」，并按串行拓扑指出应重点排查的 M-1↔M 链路。
3. 结论必须包含**时间线**：异常发生时间、（若有）主站退出时间、持续时间、恢复时间（未恢复则写“截至日志末尾未恢复”），时间取日志真实时间戳。
4. 结论要简短、准确、唯一，但主站异常不能只写一句话，需覆盖「时间线 / 最终结论 / 触发原因 / 排查建议」四块。
5. 依据日志中真实出现的信号下结论，不臆造未出现的字段。

## 一、EtherCAT 主站定位电机通信掉线问题方法

EtherCAT 通信异常通常分两类：
- 固件/软件问题（驱动器主动退出、状态异常）
- 硬件问题（线缆、电源、PHY、连接器等导致的链路断线）

### 定位方法（按顺序执行）

**Step 1：确认是否为「通信掉线」而非驱动器主动异常**

查看主站日志中电机状态字打印：
```
[mros::Time::now = ...] N号电机掉有些问题, 状态字是 0x%x 错误代码是 0x%x
```
判断规则：
- 状态字 == 0x0 → 主站已无法与该从站通信（通信掉线），继续 Step 2。
- 状态字 != 0x0 → 属于驱动器自身异常/固件逻辑问题，**不是硬件断线**，转「二、驱动故障保护机制」判定，流程结束。

**Step 2：确认掉线电机对应的从站号**

- 确认是几号电机掉使能。
- 依据本文「## 二、双臂 EtherCAT 网络拓扑与从站号对照表」查出该电机对应的从站号（寻址方式为 slave），记为 M。
- EtherCAT 为串行（菊花链）拓扑：从站 M 异常，需重点检查 **M-1 与 M 之间**的链路。

**Step 3：检查链路状态（Link Status）**

查找日志：
```
slave = %d, link_status = 0x%x, ret = %d
```
重点看**从站 (M-1)** 的 link_status：
- link_status == 0x5617 → 明确结论：从站 (M-1) 与从站 (M) 之间**硬件断线**。
- link_status == 0x5a37 → 未直接判定断线，继续 Step 4。

**Step 4：检查 EtherCAT 链路错误计数器**

查找从站错误计数（示例 `[87]~[91]` 各端口帧错误/丢链计数），重点字段：
```
[90] 'EtherCAT lost link cnt of port1' : X
```
判断规则：
- 从站 (M-1) 的 lost link cnt of port1 > 0 → 明确结论：从站 (M-1) 与从站 (M) 之间**硬件断线**。
- 所有 lost link cnt 均为 0 → 排除硬件断线，归类为固件/软件导致的 EtherCAT 通信异常。

### 最终结论判定表

| 检查项 | 结果 | 结论 |
| --- | --- | --- |
| 状态字 | ≠ 0 | 驱动器固件问题（见「三」） |
| 状态字 | = 0 | 进入硬件排查 |
| 前一从站 link_status | 0x5617 | 硬件断线，排查线束/硬件 |
| 前一从站 link_status | 0x5a37 且 lost link cnt > 0 | 硬件断线，排查线束/硬件 |
| 前一从站 link_status | 0x5a37 且 lost link cnt = 0 | 固件/软件导致的通信异常 |

### 关键信号速查（日志正则要点）

- `[90]=1`：Master↔Slave1 或 Slave1↔Slave2 之间链路丢失（lost link cnt of port1）。
- `[92]=1`：Slave7↔Slave8 之间链路丢失。
- `[8a]=255`：从站向上游发送大量错误帧（error rx frames of port1 饱和）。
- `ret=-3`：从站离线（SDO/链路访问返回失败）。
- `0xf10b` / `ethercat exit`：EtherCAT 主站退出。
- `link_status=0x5617`：明确硬件断线；`link_status=0x5a37`：需结合 lost link cnt 复核。

## 二、EtherCAT 网络拓扑与从站号对照表（按机器形态）

> 用途：诊断 Step 2「确认掉线电机对应的从站号」。定位到掉线电机后，先按 SN 前缀判断机器形态，再查对应形态的对照表拿到其 slave 号 M，最后按串行拓扑重点排查 **M-1 与 M 之间**的链路。纸面向上为机器人正面朝向。
> **重要：不同形态电机数量与拓扑不同，必须先按下方 SN 前缀选对表——双臂（DACH）用 2.1、双足（SF）用 2.2，切勿混用。**

### 机器形态识别（按 SN 前缀）

| SN 前缀 | 机器形态 | 对应拓扑表 |

| `SF` | 双足机器 | 见 2.2（12 从站） |

### 2.1 双臂（DACH）拓扑结构（串行菊花链 + 分支器）

- 中心为 **ECAT HUB**，下挂两条手臂分支，各自经一个 CU1128 分支器接入：
  - **右手（图中左侧 / 网口1）**：分支器 **CU1128 = slave 10**。
    - CU1128 `Port3 (X4)` → 右手主链：`motor8(slave11) → motor9(slave12) → motor10(slave13) → motor11(slave14)`；再从 motor11 向下串接末端 4 节：`motor12(slave15) → motor13(slave16) → motor14(slave17) → 末端转接板(slave18)`。

## 三、Tron2 电机驱动故障保护机制说明（驱动版本 V1.0.24）

当电机状态字 != 0x0 时，问题在驱动器侧，是驱动固件按**故障码**执行的保护动作（停机类=驱动器失能，限额类=驱动器降功率/限扭），而非主站与从站之间的硬件断线。按状态字打印里的 `错误代码是 0x%x` 对照下表定位：

| 故障名称 | 故障码 | 类型 | 触发条件（简） | 恢复条件 | 等级 |
|---|---|---|---|---|---|
| 无故障 | 0x0000 | 无故障 | 当前无故障码 | 无故障无告警时解除限额 | / |
| 母线过流 | 0xFF01 | 停机 | 硬件过流中断（6017母线60A/8920母线120A；峰值相电流超阈值） | 重启恢复 | 故障 |
| 过压 | 0x3210 | 停机 | 母线电压 > 75.0V | 电压回 24<V≤75V 后控制字写128清除 | 故障 |
| 欠压 | 0x3220 | 停机 | 母线≤18V 立即报；≤24V 持续0.5s | 电压回 24<V≤75V 后控制字写128清除 | 故障 |
| 电机堵转 | 0x7121 | 停机 | 速度<3rpm 且 Q轴电流≥额定×1.5 持续≥10s（Q轴电流越大时间越短，最短1.6s） | 低于检测条件后控制字写128清除 | 故障 |
| 电机过速 | 0x8400 | 停机 | 反馈速度绝对值 > 2×峰值转速 | 低于检测条件后控制字写128清除 | 故障 |
| 电机低温 | 0x4420 | 停机 | 电机温度 ≤ -20℃ 持续3.0s | 温度>-20℃ 控制字写128清除 | 故障 |
| 驱动器高温 | 0x4310 | 限额 | MOS>110℃ 持续≥0.2s | 温度<80℃ 自动清除、解除限扭 | 警告 |
| 驱动器低温 | 0x4320 | 限额 | MOS≤-20.0℃ 持续≥3.0s | 温度>-20℃ 自动清除、解除限扭 | 警告 |
| 电机高温 | 0x4400 | 停机 | 电机温度>130℃ 持续≥0.2s | 温度<100℃ 控制字写128清除 | 故障 |
| 电机峰值电流过载 | 0x7122 | 限额 | i_d²+i_q² > (0.9·i_peak)² 持续>5s | 低于检测条件自动清除、解除限扭 | 警告 |
| 驱动器峰值电流过载 | 0x2221 | 限额 | i_d²+i_q² > (0.9·i_peak)² 持续>3s | 低于检测条件自动清除、解除限扭 | 警告 |
| 电机累计热量过载 | 0x3230 | 限额 | (i_d²+i_q²-i_motor_rate²) 周期累计 > 5·i_motor_peak² | 低于检测条件自动清除、解除限扭 | 警告 |
| 驱动器累计热量过载 | 0x2222 | 限额 | (i_d²+i_q²-i_driver_rate²) 周期累计 > 3·i_driver_peak² | 低于检测条件自动清除、解除限扭 | 警告 |

判定与排查规则：
1. **状态字非 0 = 驱动器按故障码进入保护**：优先按 `错误代码是 0x%x` 查上表定位，而不是排查线束。
2. **停机类=故障（驱动器失能）**：0xFF01/0x3210/0x3220/0x7121/0x8400/0x4420/0x4400，按恢复条件处理（多为控制字写128清除，或电压/温度回正常，母线过流需重启）。
3. **限额类=警告（降功率/限扭，不失能）**：0x4310/0x4320/0x7122/0x2221/0x3230/0x2222，低于检测条件后多自动清除、解除限扭。
4. 常温下出现低温类故障（0x4420 / 0x4320）优先怀疑温度传感器硬件异常。
5. 驱动器故障保护触发后电机使能被切断（掉使能），但主站与该从站的**通信链路仍在**（状态字可读到非 0 值），据此与「通信掉线（状态字=0）」区分开。

## 四、典型根因模板（供直接套用结论）

### 模板 A：遥控器控制主站手动掉电/上电（瞬时自恢复）
命中特征：`ecm err` / `EV_EXP_ECM` / `ethercat exit` 后十几秒到几十秒内出现 `ethercat ok` / `ecm ok` / `EV_EXP_RELEASE_ECM` 自恢复；ethercat 侧 `EcMainCreateApp failed` / `End programm` / `code:131076 ethercat exit` 后重启恢复；**且无**上述硬件断线证据（状态字 0x0、`link_status=0x5617/0x5a37`、`lost link cnt of port1 > 0`）。

- 根因结论固定写：**遥控器控制主站手动掉电/上电导致的瞬时 ECM 异常，并已自恢复**。
- 不要笼统写成「硬件断线」「主站应用创建失败根因不明」。除非日志另有反证。
